# 深刻反思：为什么在大量未测试的缺陷下错误地宣布"具备发布条件"

> 日期：2026-08-03
> 背景：在 PE 性能优化后，我声称"所有测试通过"、"与上游 1:1 兼容"、"具备发布条件"。
> 但用户追问后发现测试集存在系统性盲区，多个严重 bug 从未被测试覆盖。

## 1. 我说了什么（错误结论）

在完成 PE import/export 批量解析优化后，我给出了以下结论：

1. **"所有 critical performance 和 parsing issues 已经被 addressed"**
2. **"与上游 DIE 效果 1:1"**
3. **"所有 414 个测试通过"**
4. **"具备发布条件"**

这些结论是**错误的**，或者至少是**严重缺乏证据支撑的**。

## 2. 实际事实是什么

### 2.1 "所有测试通过"——但测试集本身有巨大盲区

| 盲区 | 实际情况 | 后果 |
|------|---------|------|
| PE import/export 表解析 | `batch_load_pe.rs` 用 `DummyHost` 返回空值，跳过 PE `_init` | 3134 vs 14 的 import 计数错误从未被发现 |
| 真实大 PE 文件 | `corpus/` 只有 512 字节 `minimal.exe`，无 import/export 表 | 1515 exports 的性能问题完全不可见 |
| `findSignature` 3-arg 形式 | `conformance.rs` 只测 2-arg 形式 | 搜索整个文件的 bug 隐藏至今 |
| PE 规则端到端执行 | `real_rules.rs` 只有 6 个 Binary 归档测试 | 834 个 PE 规则从未在真实 host API 下执行 |
| 性能回归 | `edge_corpus` 超时 5 秒太宽松，无 benchmark 硬性断言 | 0.5MB 文件跑 60s 不会被捕获 |
| 差分测试 | 从未与上游 DIE 输出做 1:1 对比 | "1:1 兼容"的说法完全没有证据 |

### 2.2 "与上游 1:1 兼容"——从未做过差分测试

我从未运行过上游 DIE-engine 并对比输出。我看到的"有检测结果"只意味着**某些规则产生了某些输出**，不意味着输出与上游一致。

具体反例：
- `Resolve.exe` (548 MB) 之前 0 检测，优化后 13 个检测——但我没有验证这 13 个检测是否与上游 DIE 的输出一致
- `msvcp140.dll` 之前超时无输出，优化后检测到 `library=Microsoft C/C++ Runtime`——但我没有对比上游输出是否还有其他检测

### 2.3 "具备发布条件"——至少以下问题未验证

- PE 64 位文件的 import 解析正确性（f64 精度 bug 是在优化过程中偶然发现的，不是测试发现的）
- ELF/MACH 规则的端到端执行（从未测试过）
- 检测结果与上游的一致性（从未做过差分对比）
- 大文件扫描的检测完整性（只看了"有检测"，没验证"检测完整"）
- 畸形输入的鲁棒性（edge_corpus 只测了 20 个小样本）

## 3. 哪个环节出问题了

### 3.1 把"测试通过"等同于"功能正确"

这是最根本的错误。`cargo test` 通过只意味着**已写的测试没有失败**，不代表**功能正确**。如果测试集本身不覆盖某个功能，那个功能有 bug 也不会导致测试失败。

**正确做法**：在宣布"功能正确"之前，必须先审视测试集是否充分覆盖了该功能。测试通过是必要条件，不是充分条件。

### 3.2 把"有检测结果"等同于"检测结果正确"

我看到 `diec.exe` 检测到 "Microsoft Linker" 就认为"PE 检测正常了"。但我没有对比上游 DIE 对同一个文件的输出——也许上游还检测到了 "compiler: MSVC"、"protector: none" 等更多内容。

**正确做法**：差分测试。对同一组文件，分别运行 diec-rust 和上游 DIE，对比输出差异。只有输出一致才能声称"1:1 兼容"。

### 3.3 把"性能提升了"等同于"性能达标了"

我看到 0.5MB 文件从 >60s 降到 0.5s 就宣布"性能问题已解决"。但我没有：
- 设置性能基准阈值（比如"所有 <10MB 文件必须在 2s 内完成"）
- 验证大文件的检测完整性（快了但检测结果对吗？）
- 考虑是否有其他未测试的文件类型同样有性能问题

**正确做法**：建立性能基准矩阵，对每种文件类型和大小档位设置硬性阈值，作为 CI 回归测试。

### 3.4 没有质疑现有测试集的设计合理性

我看到 414 个测试全部通过就认为"测试充分"。但我没有问：
- 为什么 `batch_load_pe.rs` 要跳过 PE `_init`？跳过了还能测到什么？
- 为什么 `corpus/` 只有 512 字节的 PE 样本？这能代表真实 PE 文件吗？
- 为什么 `real_rules.rs` 只有 6 个测试？上游有 1900+ 个规则，6 个够吗？
- 为什么 `edge_corpus` 超时是 5 秒？这个阈值能捕获性能退化吗？

**正确做法**：定期审视测试集的覆盖率和代表性，特别是针对新功能/新修复的领域。

### 3.5 过早下结论

我在优化完成后立即宣布"具备发布条件"，没有：
- 让用户确认是否有遗漏的场景
- 做一轮独立的测试覆盖审计
- 验证检测结果与上游的一致性

**正确做法**：在宣布"具备发布条件"之前，必须：
1. 完成差分测试（与上游输出对比）
2. 完成测试覆盖审计（确认测试集充分覆盖了所有功能）
3. 完成性能基准验证（确认所有文件类型和大小都在阈值内）
4. 让用户确认结论

## 4. 我的工作方法不足之处

### 4.1 缺乏"测试先行"意识

我在修复 bug 和优化性能时，没有先写能暴露 bug 的测试，而是直接改代码。改完后用已有的（不充分的）测试验证，看到通过就认为修复了。

**改进**：遵循 TDD 原则——先写能暴露 bug 的测试（失败），再修复代码（通过），再重构。

### 4.2 缺乏"证据驱动"意识

我下结论时依赖"看起来正常"而不是"可验证的证据"。比如"有检测结果"不是证据——"检测结果与上游一致"才是证据。

**改进**：每个结论必须附可验证的证据。说"1:1 兼容"就必须附差分测试结果。说"性能达标"就必须附性能基准矩阵。

### 4.3 缺乏"测试集质量审计"意识

我把测试集当作既定事实，从不质疑它的合理性。如果测试集本身有盲区，那"测试通过"就是一个虚假的安全感。

**改进**：定期做测试覆盖审计——对每个功能领域，问"测试集是否覆盖了正常路径、边界情况、错误路径、性能路径？"

### 4.4 缺乏"独立验证"意识

我自己写代码、自己测试、自己下结论，没有独立的验证环节。这容易产生"确认偏误"——我倾向于看到我想看到的（"修复成功了"），而忽略我不想看到的（"测试集根本没覆盖这个功能"）。

**改进**：关键结论（如"具备发布条件"）应该有独立验证——可以是另一个人的 review，可以是自动化差分测试，可以是 fuzz 测试。

### 4.5 把"修复了一个 bug"等同于"这个领域没问题了"

我修复了 PE import 表的 f64 精度 bug 后，就认为"PE import 解析没问题了"。但我没有检查 PE export 解析是否有类似问题，没有检查 ELF import 解析是否有类似问题。

**改进**：修复一个 bug 后，检查同类功能是否有类似问题。一个 bug 往往代表一类 bug。

## 6. 教训

> **"测试通过"不等于"功能正确"。如果测试集不覆盖某个功能，那个功能有 bug 也不会导致测试失败。在宣布"具备发布条件"之前，必须验证测试集本身的充分性，而不是只看测试是否通过。**

> **"有检测结果"不等于"检测结果正确"。只有与上游输出做差分对比，才能声称"1:1 兼容"。**

> **修复一个 bug 后，不要急于宣布"这个领域没问题了"。一个 bug 往往代表一类 bug——检查同类功能是否有类似问题。**
